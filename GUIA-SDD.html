Spec-Driven Development

Cómo preparamos y construimos software: primero el qué, después el cómo. Con la IA como aliada, sin perder el control.

Guía de referencia
Para equipo, programadores y clientes.
Inspirada en el arnés betta-tech/harness-sdd y adaptada por Flama Studio.

1. Qué es esto y por qué importa

El problema que resolvemos antes de escribir una sola línea.

La inteligencia artificial ya escribe código. La pregunta importante ya no es si puede, sino cómo conseguir que escriba el código correcto. La respuesta no está en usar un modelo más nuevo, sino en el método con el que se trabaja.

Spec-Driven Development (SDD) es desarrollo guiado por la especificación. Primero se describe con claridad qué debe hacer el software (la spec), y solo después se construye el código a partir de esa spec. La especificación es la fuente de verdad: si algo no está en la spec, no se construye.

Piensa en construir una casa. La spec son los planos del arquitecto. Nadie pone un ladrillo antes de tener los planos aprobados. En el desarrollo improvisado, mucha gente empieza a poner ladrillos "a ver qué sale" — y así aparecen las chapuzas y los sobrecostes.

Harness Engineering vs SDD (no son lo mismo)

Conviene separar dos conceptos que suelen confundirse:

ConceptoQué es
Harness EngineeringLa disciplina de automatizar un flujo de trabajo con IA. Un "arnés" es el conjunto de reglas y ficheros que obligan a la IA a trabajar de una forma concreta en vez de improvisar.
SDDUn flujo de trabajo concreto: spec primero, código después.

Es decir: usamos harness engineering para construir un arnés que implementa SDD. Con la misma técnica se podría montar un arnés para otro método (TDD, ágil…). Nosotros montamos uno para SDD.

El "arnés" no es nada mágico ni complejo: son ficheros de texto que le dicen a la IA cómo comportarse, qué pasos seguir y qué no saltarse. Eso es todo.

2. Los principios que lo hacen funcionar

El "por qué" detrás de toda la estructura.

  1. El estado vive en disco, no en el chat. Todo (requisitos, decisiones, progreso) se guarda en ficheros. Si se cierra la sesión hoy y se retoma mañana, no se pierde nada. El chat se olvida; los ficheros no.
  2. Una cosa a la vez. Se completa una funcionalidad antes de empezar la siguiente. Nada de diez cosas a medias.
  3. El humano dentro del bucle. Una persona aprueba en dos momentos clave (el diseño y los tests). La IA no trabaja sola mientras nadie mira. Se mantiene el control.
  4. Trazabilidad: 1 requisito → 1 test. Cada requisito se comprueba con una prueba automática. Así se sabe, de verdad, si está bien hecho.
  5. Cada agente, su contexto. En lugar de un único "chat gigante" que se lía, hay agentes especializados y cada uno recibe solo lo que necesita.
  6. Selectivo, no para todo. Las tareas triviales no pasan por todo el ritual. Solo lo importante.
Lo verdaderamente valioso no es copiar la herramienta de otro, sino construir la propia, que funcione como trabaja cada equipo. Esta metodología es un punto de partida pensado para evolucionar.

3. Las dos fases de un proyecto

Primero saber qué hay que hacer. Luego hacerlo.

Fase A · Descubrimiento

Objetivo: saber QUÉ hay que construir.

Quién lleva la voz: la IA, haciendo de Analista, entrevista y guía.

Resultado: requisitos claros + los cimientos del proyecto.

Fase B · Construcción

Objetivo: construirlo bien.

Quién lleva la voz: el arnés de agentes (leader, spec_author, implementer, reviewer).

Resultado: código que cumple los requisitos y está probado.

El mapa completo

TÚ + EL CLIENTE │ ▼ ┌──────────────────────────────────────────────┐ │ FASE A · DESCUBRIMIENTO │ │ (la IA hace de "Analista" y te entrevista) │ │ · Estado actual · Visión de negocio │ │ · Procesos y flujos · Requisitos (EARS) │ │ · Modelo de datos · Integraciones │ │ + CIMIENTOS: arquitectura · convenciones │ └───────────────────┬────────────────────────────┘ │ ⛳ ¿"Definición de listo"? ▼ ┌──────────────────────────────────────────────┐ │ EL PUENTE → la carpeta ya es un proyecto │ │ listo para el arnés. Mismo punto de partida. │ └───────────────────┬────────────────────────────┘ ┌───────────┴───────────┐ TÚ con IA DEV HUMANO ▼ ▼ ┌──────────────────────┐ ┌────────────────────┐ │ FASE B · arnés │ │ Entregas la Fase A │ │ leader → spec_author │ │ como requisitos + │ │ → 🧍 apruebas spec │ │ CHECKPOINTS como │ │ → implementer │ │ criterios de "hecho"│ │ → 🧍 apruebas tests │ └────────────────────┘ │ → reviewer → DONE │ └──────────────────────┘
Flujo mixto: al acabar la Fase A se decide quién construye. Si lo hace la IA, se entra en la Fase B. Si lo hace un programador humano, se le entrega el resultado de la Fase A como documento de requisitos. En ambos casos, el trabajo duro de pensar el qué ya está hecho.

4. Fase A — El Analista te acompaña

Pensada para quien dirige el proyecto sin ser programador.

En esta fase la IA no espera a que le digan exactamente qué pedir: entrevista, guía y decide cuándo hay información suficiente. Aporta el método y las preguntas correctas; la persona aporta el conocimiento del negocio y del cliente.

Qué hace el Analista

  • Hace las preguntas de una en una (opción múltiple cuando se puede).
  • Explica antes de preguntar: ningún tecnicismo sin traducir.
  • Escucha la historia del cliente aunque venga desordenada, y la reformula para confirmar.
  • Detecta los huecos y los anota como dudas o pendientes.
  • Avisa cuándo ya hay suficiente mediante una "Definición de listo".

Qué se produce

DocumentoQué captura
Estado actualQué usa hoy el cliente (si hay sistema previo).
Visión de negocioEl para qué, el dolor que se resuelve, el éxito.
Procesos y flujosCómo trabaja el cliente de verdad, paso a paso.
Requisitos (EARS)Lo que el software debe hacer, comprobable con tests.
Modelo de datosQué información se guarda y cómo se relaciona.
IntegracionesCon qué otros sistemas hay que conectar.
CimientosArquitectura, convenciones y formato de specs.
Donde quien dirige no tenga criterio técnico, el Analista propone valores por defecto sensatos y explica el porqué. No es hacer trampa: lo que afecta al negocio lo decide la persona; lo puramente técnico, la IA.

Cómo se garantiza no olvidar nada (motor anti-olvidos)

Los requisitos no se sacan de memoria ni "uno a uno": emergen de hablar del negocio. La persona cuenta historias y procesos; la IA los convierte en requisitos y los devuelve para confirmar (reconocer es más fácil que recordar). La completitud la garantiza un recorrido sistemático:

  1. Recorrido del proceso — el camino normal, paso a paso.
  2. Barrido "¿qué pasa si…?" — sobre cada acción: falta un dato, ya existe, falla el otro sistema, quién puede hacerlo, límites, deshacer…
  3. Las 5 operaciones por entidad — crear, ver, buscar/listar, editar, borrar.
  4. Categorías transversales — validaciones, estados, permisos, avisos, informes, integraciones, auditoría, cálculos, migración…
  5. Repaso final — "¿reconoces todo tu negocio aquí? ¿falta alguna excepción rara?".
Se trabaja por capas: primero lo esencial para arrancar; el resto, en una segunda pasada o anotado como pendiente. Así la fase nunca se bloquea, pero nada se pierde. Y siempre se puede pedir "más cobertura": la IA seguirá generando preguntas hasta agotar el tema.

5. Cómo se escriben los requisitos: EARS

Una plantilla sencilla para que cada requisito se pueda probar.

EARS es una forma de escribir cada requisito con un patrón fijo: "Cuando [situación], el sistema debe [comportamiento concreto]." La gracia: cada requisito así escrito se convierte directamente en un test.
TipoPatrónEjemplo
EventoCuando [evento], el sistema debe [respuesta].Cuando el usuario guarda un cliente, el sistema debe mostrarlo en el listado.
Condición/errorSi [condición], entonces el sistema debe [respuesta].Si falta el email, el sistema debe rechazar el guardado y avisar.
EstadoMientras [estado], el sistema debe [respuesta].Mientras se carga, el sistema debe mostrar un indicador.
SiempreEl sistema debe [respuesta].El sistema debe registrar quién hizo cada cambio.

Por qué EARS y no historias de usuario: una historia de usuario puede ser vaga ("como usuario quiero gestionar clientes"). Un requisito EARS es concreto y verificable: se sabe exactamente qué comprobar. Cada R → al menos un test.

6. Fase B — El arnés de agentes

La IA construye; el humano supervisa en dos puertas.

Los cuatro agentes

AgenteSu trabajoNunca hace
leader (jefe)Mira el estado y lanza al agente que tocaEscribir código
spec_authorConvierte un requisito en 3 ficheros (qué/cómo/pasos)Implementar
implementerEscribe el código siguiendo las tareasAuto-aprobarse
reviewerValida specs ↔ tests, convenciones y "terminado"Modificar código

Ningún agente aprueba su propio trabajo: así se evita el conflicto de interés y se mantiene la calidad.

Los tres ficheros de cada spec

  • requirements.md — QUÉ hay que hacer (requisitos EARS).
  • design.md — CÓMO se hace (decisiones técnicas, qué se toca y qué no).
  • tasks.md — los PASOS concretos que ejecuta el implementer.

El flujo de estados y las dos puertas

pending ──(spec_author redacta las 3 specs)──▶ spec_ready │ 🧍 APRUEBAS ◀────── PUERTA 1 (diseño) ▼ in_progress (implementer escribe el código) │ 🧍 REVISAS ◀─────── PUERTA 2 (tests) ▼ (reviewer valida todo) ──▶ done
🧍
Puerta 1 — tras la spec. ¿Es de verdad lo que queremos construir? El agente se para y espera aprobación antes de escribir una línea de código.
🧍
Puerta 2 — tras los tests. ¿Las pruebas tienen sentido y cubren lo importante? Se revisa antes de cerrar.
SDD no es para todo. Cada funcionalidad lleva una marca sdd: true (pasa por todo el ritual) o sdd: false (cambio pequeño, sin ceremonia). El criterio evita que un cambio trivial cueste más esfuerzo del que vale.

7. Cómo se usa, en la práctica

De carpeta vacía a proyecto en marcha.

  1. Se copia la plantilla del framework a la carpeta del cliente/proyecto.
  2. Se arranca la Fase A: se le da a la IA el prompt de inicio y empieza la entrevista guiada.
  3. Se responde hasta que el Analista confirma que hay información suficiente ("Definición de listo").
  4. Se decide quién construye: la IA (Fase B) o un programador humano (se le entrega la Fase A).
  5. Si construye la IA: se le pide "implementa la siguiente tarea pendiente" y se aprueba en las dos puertas.
  6. Cada funcionalidad terminada queda registrada en el historial. Se repite con la siguiente.
La IA acelera enormemente el trabajo, pero la experiencia y el criterio humano no se delegan. Se revisa el diseño y se revisan los tests. Ese es el seguro de calidad.

Para el programador (si construye una persona)

Se entrega la carpeta de descubrimiento como documento de requisitos y el fichero de checkpoints como criterios de aceptación. El valor es el mismo: alguien ya ha hecho el trabajo de definir, con precisión, qué hay que construir.
